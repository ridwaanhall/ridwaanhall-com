# Schema

`0000_init.sql` is the schema. Not a starting point that later files amend —
the whole of it, as it stands, in one file that runs against an empty database:

```bash
node scripts/apply-migration.mjs drizzle/0000_init.sql          # dry run
node scripts/apply-migration.mjs drizzle/0000_init.sql --apply
```

Over `STORAGE_POSTGRES_URL_NON_POOLING`, never the pooled URL — DDL is not
reliable through pgbouncer's transaction-mode pooling. `apply-migration.mjs`
wraps the file in one transaction and rolls it back unless `--apply` is given,
so the dry run shows you exactly what would execute.

## Changing it

Edit `0000_init.sql` so it describes the schema you want, apply the change to
the database, then bring the two derived things back into step:

```bash
npx tsx scripts/check-baseline-schema.mjs   # the file still builds this schema
node scripts/gen-app-schema.mjs             # regenerate the Drizzle mapping
npx tsx scripts/check-app-schema.mjs        # the mapping still matches
```

`check-baseline-schema.mjs` applies the file into a scratch schema inside a
transaction, compares the result against the live one table by table and
constraint by constraint, and rolls back. It is what keeps this file honest: a
column added by hand and never written down here would leave the mapping
agreeing with the database while this file quietly described something else.

**One file rather than a numbered sequence.** A ladder of migrations earns its
keep when several deployments are at different rungs and each has to climb. One
database and one deployment do not have that problem, and the cost is real: a
new installation has to replay every step in order, including the ones that only
made sense against data that no longer exists. Git history is where the sequence
lives.

## Write the SQL by hand

`drizzle-kit generate` is not used here and `drizzle-kit migrate` has never run
against this database. Generate does not model row-level security: it reads
every table as "should be disabled" and emits `DISABLE ROW LEVEL SECURITY` for
all of them, which is the one statement that must never execute here. Pull does
not help either — pointed at `schemaFilter: ["app"]` it fetches zero tables,
which is why the Drizzle mapping is generated by `scripts/gen-app-schema.mjs`
from `information_schema` instead.

So the DDL is written by hand, and any SQL a tool produces gets read line by
line before it runs.

## Do not give a file its own transaction

`apply-migration.mjs` wraps the whole file in one transaction. A `begin` or
`commit` inside ends that transaction from the inside, so a dry run commits and
still reports that nothing changed. The script refuses a file that carries its
own transaction control.

A PL/pgSQL `DO $$ ... BEGIN ... END $$` block is not transaction control and is
allowed — its `BEGIN` opens a block, not a transaction. Dollar-quoted bodies are
blanked before that check runs.

## `9999_drop_public.sql`

Not part of the schema. It removes the tables the site's previous build left in
`public`, and it must not run until the domain serves this application — the
file's header has the pre-flight and the order to do it in. Delete it, and the
two scripts its header names, once it has run.
